# VEDA Diagnostics Agent

## 1. Purpose
The Diagnostics Agent analyzes the `MonitoringResult` and associated anomaly evidence to determine the probable cause and affected subsystem of an abnormal vehicle condition. It acts as the second stage in the Agentic AI pipeline.

The Diagnostics Agent does **NOT**:
- Recalculate or modify prognostic RUL.
- Create maintenance schedules or override downstream planning.
- Invent missing sensor data.
- Predict ground-truth failures without evidence.

## 2. Inputs
The agent expects a strictly typed `DiagnosticsInput` schema via the service interface:
- `monitoring_result` (`MonitoringResult` object from the upstream Monitoring Agent)
- `telemetry` (dict of numerical sensor readings, optional)
- `rf_abnormal_class` (string: specific routing label if available)
- `fault_codes` (list of active fault strings)

*All inputs are validated using Pydantic. Any inclusion of prohibited fields will be rejected.*

## 3. Outputs
The agent returns a `DiagnosticsResult`:
- `vehicle_id`
- `timestamp`
- `problem_detected` (string: high-level summary of the issue or "NONE")
- `evidence_sensors` (list of supporting data points used for the diagnosis)
- `probable_cause` (string: diagnostic interpretation)
- `confidence` (float: extracted strictly from RF probability, never fabricated)
- `next_diagnostic_action` (string: "CONTINUE_MONITORING", "TRIGGER_MAINTENANCE_PLANNING", "HUMAN_REVIEW", "AWAIT_VALID_DATA")
- `status` (string: "SUCCESS", "CONFLICT", "INSUFFICIENT_EVIDENCE")
- `execution_metadata` (agent version and execution time)

## 4. Decision Logic & Error States
- **Insufficient Evidence:** If the `MonitoringResult` itself indicates invalid or missing data, the agent halts diagnosis and returns `status=INSUFFICIENT_EVIDENCE`.
- **Conflict Handling:** If the evidence is fundamentally contradictory (e.g., fault codes present but RF explicitly normal without abnormality), it flags `status=CONFLICT` and delegates to `HUMAN_REVIEW`.
- **Abnormal Diagnosis:** If an abnormality is confirmed, it synthesizes the `rf_abnormal_class` and `fault_codes` into a cohesive `probable_cause`. If neither is present but RF flagged an anomaly, it reports an "Unknown subsystem affected."

## 5. RUL Boundary
The Diagnostics Agent strictly operates on diagnostic (current-state) abnormality and fault identification. It does not ingest, alter, or replace the `Fusion_RUL` values generated by the frozen prognostic ML pipeline.

## 6. Vehicle Isolation
Like the Monitoring Agent, the Diagnostics Agent relies on the `vehicle_id` and strict data boundaries to ensure that Tank-specific telemetry is never evaluated under Logistic/Officer rules. The shared schema logic applies generically to both vehicle classes without leaking specific models.

## 7. Test Coverage
Unit tests (`tests/test_diagnostics_agent.py`) verify:
- Accurate evidence aggregation and probable cause synthesis.
- Resolution of conflicting inputs (forcing human review).
- Correct handling of insufficient upstream monitoring data.
- Complete absence of fabricated RUL fields or leaked ground-truth.
